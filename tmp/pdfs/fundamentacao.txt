Fundamentação teórica do minicurso de Git e 
GitHub
Este material prepara o instrutor para o minicurso. Os assuntos aparecem na mesma ordem em que 
serão trabalhados com a turma, sem depender de slides, horários ou códigos internos de 
planejamento. A proposta é permitir uma leitura contínua, como um pequeno livro. Depois da leitura, 
o instrutor deverá conseguir explicar os conceitos com palavras próprias, relacionar cada comando 
ao que o Git está fazendo e responder às dúvidas mais comuns de estudantes iniciantes.
O curso começa pelo controle de versões, apresenta o funcionamento local do Git, avança para 
commits, branches e merges e, por fim, situa o GitHub no trabalho colaborativo. A prática Git 
Multiverse retoma esses conceitos em um repositório local. Os alunos usarão Fedora ou Linux Mint 
com Bash, mas os conceitos de Git são os mesmos nas duas distribuições.
1 Controle de versão
1.1 O problema de trabalhar sem histórico
É comum começar um trabalho criando um arquivo e, depois de algumas alterações, salvar cópias 
com nomes como trabalho-final, trabalho-final-v2 e trabalho-final-agora-vai. Essa estratégia 
parece funcionar enquanto há poucos arquivos e uma única pessoa trabalhando. O problema 
aparece quando precisamos descobrir qual cópia é a mais recente, recuperar uma parte apagada ou 
entender por que determinada mudança foi feita.
Copiar pastas também não explica o histórico. Sabemos que existem versões diferentes, mas não 
sabemos com clareza quem alterou cada arquivo, quando a mudança ocorreu ou qual era sua 
finalidade. Em um projeto de software, no qual muitos arquivos podem mudar, esse método se torna 
difícil de controlar.
O controle de versão resolve esse problema ao registrar estados identificáveis do projeto. Cada 
registro preserva o conteúdo escolhido naquele momento e inclui informações que ajudam a 
compreender sua origem. Assim, podemos consultar versões anteriores, comparar mudanças e 
experimentar novas ideias sem perder uma versão que já funciona.
1.2 O que um sistema de controle de versão registra
Um sistema de controle de versão mantém um histórico organizado. Ele não serve apenas para 
guardar cópias de segurança. Seu objetivo principal é explicar a evolução do projeto. Um bom 
histórico permite descobrir qual mudança introduziu um arquivo, qual era o estado anterior e quais 
alterações pertencem a uma funcionalidade.
O histórico também facilita o trabalho em equipe. Cada pessoa pode desenvolver uma alteração em 
uma linha separada, registrar seu progresso e integrar o resultado quando estiver pronto. Mesmo 
quando uma única pessoa trabalha no projeto, essa separação ajuda a testar ideias com segurança.
1.3 Controle de versão e backup
O Git preserva o histórico dentro do repositório, mas um repositório armazenado somente em um 
computador ainda pode ser perdido se o disco falhar. Controle de versão e backup resolvem 
problemas relacionados, mas diferentes. O Git organiza a evolução dos arquivos. Uma cópia em 
outro dispositivo ou servidor protege o repositório contra a perda do equipamento.

Durante o minicurso, os alunos trabalharão localmente. Isso é suficiente para aprender commits, 
branches e merges. Em projetos reais, costuma-se manter uma cópia remota em uma plataforma 
como o GitHub, além de outras medidas de backup adotadas pela equipe.
2 Git e GitHub
2.1 O que é Git
Git é um sistema de controle de versão distribuído. Ele é instalado no computador e pode funcionar 
sem conexão com a internet. Ao executar comandos como git status, git add e git commit, 
estamos conversando com o programa Git e modificando um repositório local.
A palavra distribuído indica que cada cópia completa de um repositório pode conter o histórico do 
projeto. Uma pessoa não precisa consultar um servidor a cada commit. Ela pode criar commits, 
consultar versões e trabalhar com branches enquanto está desconectada. A comunicação com um 
servidor acontece quando alguém decide enviar ou receber mudanças.
O Git identifica versões por meio de códigos chamados hashes e relaciona cada commit ao commit 
anterior. Essa ligação forma o histórico. Quando há branches e merges, o histórico deixa de ser uma 
linha simples e passa a formar um grafo, isto é, uma estrutura com caminhos que podem se separar 
e se reencontrar.
2.2 O que é GitHub
GitHub é uma plataforma de hospedagem e colaboração que trabalha com repositórios Git. Ela 
oferece interface web, armazenamento remoto, controle de acesso, acompanhamento de tarefas e 
revisão de contribuições por meio de pull requests.
GitHub e Git não são sinônimos. Git é a ferramenta que registra versões. GitHub é um serviço que 
hospeda repositórios e organiza a colaboração em torno deles. Podemos usar Git sem GitHub, como 
acontecerá na maior parte do laboratório. Também existem outras plataformas compatíveis com Git.
Uma comparação útil é pensar no Git como o mecanismo que organiza o histórico e no GitHub como 
um local compartilhado no qual esse histórico pode ser publicado e discutido. Os commits são 
criados pelo Git. O GitHub recebe esses commits quando alguém executa um envio para um 
repositório remoto.
2.3 Repositório local e repositório remoto
O repositório local fica no computador da pessoa. Ele contém os arquivos de trabalho e uma pasta 
oculta chamada .git, na qual o Git armazena o histórico, as referências das branches e outras 
informações internas. Apagar essa pasta transforma o diretório em uma pasta comum e remove o 
histórico local; por isso, ela não deve ser manipulada durante a aula.
Um repositório remoto é outra cópia acessível por um endereço. Esse endereço pode apontar para o 
GitHub, para outro servidor ou até para outra pasta local. Por convenção, o primeiro remoto costuma 
receber o nome origin. Esse nome é apenas um apelido usado nos comandos.
No minicurso, os alunos não precisarão autenticar no GitHub. Eles poderão observar ou clonar um 
repositório público. Envio de commits e criação de pull request serão demonstrados apenas pelo 
instrutor.

3 O repositório e os três estados do Git
3.1 Diretório de trabalho
O diretório de trabalho é a pasta visível na qual editamos os arquivos. Quando abrimos um projeto 
no VS Code, vemos o conteúdo desse diretório. Salvar um arquivo altera o conteúdo no disco, mas 
isso ainda não cria uma versão no Git.
Essa distinção é central para quem está começando. O editor salva arquivos; o Git registra versões. 
Um arquivo pode estar salvo e ainda aparecer como modificado. Isso significa que o conteúdo existe 
no disco, mas ainda não foi incluído em um novo commit.
3.2 Área de preparação
Antes de criar um commit, escolhemos quais mudanças farão parte dele. Essa seleção recebe o 
nome de área de preparação, ou staging area. O comando git add coloca nessa área o estado atual 
dos arquivos indicados.
A área de preparação permite separar mudanças. Uma pessoa pode preparar apenas uma correção 
concluída e deixar outra mudança incompleta para depois. Em uma aula inicial, trabalharemos com 
mudanças simples, mas o princípio é o mesmo.
Executar git add não envia arquivos ao GitHub e não cria um commit. O comando apenas prepara 
conteúdo para o próximo registro local.
3.3 Repositório e histórico
Quando executamos git commit, o Git cria um novo registro com o conteúdo que estava preparado. 
Esse registro passa a fazer parte do histórico. Cada commit guarda uma identificação, informações 
de autoria, data, mensagem e ligação com o commit anterior.
O fluxo básico tem três passos. Primeiro, a pessoa modifica e salva um arquivo no diretório de 
trabalho. Depois, git add coloca a versão escolhida na área de preparação. Por fim, git commit 
registra o conteúdo preparado no histórico.
O Git não move o arquivo entre três pastas físicas. Diretório de trabalho, área de preparação e 
histórico são estados lógicos usados para entender o que será registrado.
3.4 Como o Git descreve o estado
O comando git status é a principal fonte de orientação durante a aula. Ele mostra a branch atual e 
informa se existem arquivos novos, modificados ou preparados. Antes de repetir um comando ou 
tentar corrigir um erro, devemos consultar o estado.
Um arquivo novo que o Git ainda não acompanha aparece como untracked. Depois de git add, ele 
aparece como preparado. Um arquivo já registrado que foi alterado aparece como modificado. Após 
um commit que inclui todas as mudanças preparadas, o Git informa que a árvore de trabalho está 
limpa.
Árvore limpa não significa que o projeto está correto ou publicado. Significa apenas que, naquele 
momento, não há diferenças entre os arquivos acompanhados, a área de preparação e o último 
commit da branch atual.

4 Criação e configuração de um repositório
4.1 Inicialização
O comando git init cria a estrutura interna de um repositório na pasta atual. No curso, usaremos 
git init -b main para criar o repositório já com a branch principal chamada main. Versões antigas 
do Git podem não aceitar a opção -b. Nesse caso, pode-se executar git init e depois git branch 
-M main.
É importante observar a pasta atual antes da inicialização. Se o comando for executado na pasta 
errada, o Git começará a acompanhar um conjunto de arquivos diferente do planejado. No Bash, pwd 
mostra o caminho atual e ls lista o conteúdo da pasta.
Executar git init várias vezes não corrige arquivos, commits ou branches. Quando algo parece 
errado, a primeira providência é verificar pwd, a branch e git status.
4.2 Identidade dos commits
O Git registra nome e e-mail como parte da autoria de cada commit. Esses dados não são login e 
não concedem acesso ao GitHub. No laboratório, configuraremos uma identidade fictícia apenas 
dentro de cada repositório:
git config --local user.name "Estudante"
git config --local user.email "estudante@example.invalid"
A opção --local limita a configuração ao repositório atual. Isso é adequado para computadores 
compartilhados porque evita alterar a configuração de outros projetos. Se o Git informar que não 
conhece a identidade do autor, basta definir esses dois valores e repetir somente o commit que 
falhou.
5 Commits e histórico
5.1 O que é um commit
Um commit representa um estado registrado do projeto. Ele costuma ser descrito como uma 
fotografia, mas há uma diferença importante: o commit também conhece seu antecessor. Essa 
ligação permite percorrer a história e descobrir como o projeto chegou ao estado atual.
O commit não precisa incluir todos os arquivos da pasta. Ele inclui o conteúdo que foi preparado. 
Por isso, é possível criar registros coerentes, cada um com uma finalidade.
5.2 Identificação e mensagem
Cada commit recebe um hash, exibido como uma sequência de letras e números. Os comandos 
geralmente mostram uma forma abreviada suficiente para identificar o commit dentro daquele 
repositório. Os hashes produzidos em computadores diferentes podem variar por causa de autoria, 
data ou outros metadados. Na aula, não devemos esperar que todos tenham o mesmo hash.
A mensagem explica a intenção da mudança. Mensagens como atualização ou mudanças dizem 
pouco. Uma mensagem como Adiciona personagens do universo Marvel permite compreender o 
objetivo sem abrir o conteúdo. Para iniciantes, recomenda-se uma frase curta no presente, com um 
verbo que descreva a ação.
5.3 Salvar e commitar são ações diferentes
Salvar no VS Code grava o conteúdo no arquivo. O Git percebe que o arquivo mudou, mas ainda 
não registra uma nova versão. git add escolhe o conteúdo. git commit cria o registro.

Essa diferença explica muitos erros iniciais. Se git commit disser que não há nada para registrar, 
talvez o arquivo não tenha sido salvo, talvez não tenha sido preparado ou talvez o conteúdo já esteja 
igual ao último commit. A solução começa com git status, não com a repetição automática de 
comandos.
5.4 Consulta do histórico
git log mostra os commits da branch atual, começando pelo mais recente. A opção --oneline 
resume cada commit em uma linha. Para observar branches e merges, usaremos:
git log --oneline --graph --all --decorate
--graph desenha as linhas do histórico, --all inclui todas as branches e --decorate mostra quais 
nomes apontam para cada commit. O desenho usa caracteres de texto. Ele não é uma árvore de 
pastas; representa relações entre commits.
5.5 Comparação de mudanças
git diff mostra mudanças do diretório de trabalho que ainda não foram preparadas. Depois de git 
add, essas mudanças deixam de aparecer no git diff comum porque passaram para a área de 
preparação. Para ver o que será incluído no próximo commit, usamos git diff --cached.
Um resultado vazio não deve ser interpretado isoladamente. git diff pode estar vazio enquanto há 
mudanças preparadas. Por isso, a combinação de git status, git diff e git diff --cached 
oferece uma visão mais completa.
6 Branches
6.1 O que é uma branch
Uma branch é um nome que aponta para um commit. Ela permite continuar o trabalho a partir de um 
ponto conhecido sem mover a branch principal. Ao criar novos commits nessa branch, seu nome 
avança e passa a apontar para o commit mais recente daquela linha de desenvolvimento.
Branches são leves porque o Git não precisa copiar a pasta inteira para criá-las. O repositório 
continua sendo o mesmo. O que muda é a referência ativa e, quando necessário, o conteúdo 
apresentado no diretório de trabalho.
6.2 A branch principal
Neste curso, a branch principal se chama main. Ela representa a linha na qual reuniremos o 
resultado final da prática. O nome é uma convenção. O Git não considera que toda mudança feita 
em main seja automaticamente correta; a equipe define quando e como essa branch deve ser 
alterada.
Ao iniciar o Git Multiverse, criaremos o primeiro commit em main. Em seguida, criaremos universo-
marvel e universo-dc apontando para esse mesmo commit. Isso garante que os dois universos 
tenham uma base comum e que nenhum deles nasça das mudanças exclusivas do outro.
6.3 HEAD e branch ativa
HEAD indica a posição atual do trabalho. No fluxo normal da aula, HEAD aponta para a branch 
ativa. Quando criamos um commit, a branch ativa avança para o novo commit.
O comando git branch --show-current mostra o nome da branch atual. git switch nome-da-
branch troca para uma branch existente. git switch -c nova-branch cria uma branch a partir da 
posição atual e já muda para ela.

Trocar de branch pode alterar os arquivos visíveis. Se marvel.md existe apenas em universo-
marvel, ele pode deixar de aparecer quando mudamos para universo-dc. O arquivo não foi perdido; 
ele pertence ao estado registrado na outra branch.
6.4 Independência das branches
Duas branches são independentes quando cada uma continua a partir da base escolhida, sem 
incorporar os commits exclusivos da outra. No Multiverse, Marvel e DC devem nascer do mesmo 
commit inicial. Marvel cria marvel.md; DC cria dc.md. Antes dos merges, cada branch possui seu 
próprio commit e desconhece o arquivo exclusivo da outra.
Se a branch DC for criada depois do commit Marvel enquanto estamos em universo-marvel, DC 
nascerá de Marvel e o exercício perderá o ponto principal. A ordem segura é criar os dois nomes 
logo após o commit inicial e somente depois começar as mudanças.
7 Merge e integração de históricos
7.1 O que é merge
Merge é a operação que integra uma linha de desenvolvimento em outra. Para integrar Marvel na 
principal, primeiro mudamos para main e então executamos o merge de universo-marvel. A branch 
que está ativa recebe a integração. A branch usada como origem não é apagada nem avança 
automaticamente.
Em git merge universo-marvel, o Git não muda para Marvel. Ele traz para a branch atual o 
histórico alcançado por universo-marvel. Por isso, sempre confirmamos a branch atual antes do 
comando.
7.2 Fast forward
Um merge pode acontecer por fast forward quando a branch atual não tem commits novos e a outra 
branch está simplesmente adiante no mesmo caminho. Nesse caso, o Git move o nome da branch 
atual até o commit mais recente. Nenhum commit de merge adicional é necessário.
Fast forward é uma integração válida. Durante a demonstração inicial, esse comportamento ajuda a 
mostrar que uma branch é uma referência que pode avançar.
7.3 Commit de merge
Quando duas linhas possuem commits diferentes, o Git pode criar um commit de merge com dois 
pais. Esse commit registra que os históricos foram reunidos. A opção --no-ff força a criação 
explícita desse commit mesmo quando um fast forward seria possível.
No Multiverse, usaremos --no-ff nos dois merges para tornar a integração visível no grafo. O 
resultado esperado será composto por cinco commits: um inicial, um Marvel, um DC e dois commits 
de merge.
7.4 Conflitos de merge
Um conflito ocorre quando o Git não consegue decidir sozinho como combinar mudanças. Um caso 
comum aparece quando duas branches alteram de maneiras diferentes a mesma parte de um 
arquivo. O Git interrompe o merge, marca o arquivo e pede uma decisão humana.
Conflito não significa que o repositório foi destruído. Significa que existem alternativas incompatíveis 
e alguém precisa escolher o conteúdo final. O procedimento geral é ler os marcadores, editar o 
arquivo, preparar a resolução com git add e concluir o commit. Também é possível abandonar uma 
tentativa de merge ainda não concluída com git merge --abort.

8 Repositórios remotos e GitHub
8.1 Clone
git clone cria uma cópia local a partir de um repositório existente. Além dos arquivos, o clone 
recebe o histórico e configura o endereço de origem como um remoto chamado origin.
Um repositório público pode ser clonado por HTTPS sem autenticação. Isso não dá permissão para 
enviar mudanças. Ler um repositório público e escrever nele são ações diferentes.
8.2 Push
git push envia commits e referências locais para um repositório remoto. O commit já precisa existir 
antes do push. Portanto, push não substitui git add nem git commit.
O envio normalmente exige permissão e autenticação. Como os alunos não precisarão de contas 
GitHub, somente o instrutor demonstrará essa operação em um repositório preparado anteriormente.
8.3 Fetch e pull
git fetch consulta o remoto e atualiza as referências remotas conhecidas pela cópia local, sem 
integrar automaticamente o conteúdo na branch atual. git pull combina a obtenção das 
informações remotas com uma integração na branch atual.
Para uma primeira aula, basta compreender que pull traz e integra atualizações, enquanto push 
envia commits. Em situações reais, a equipe precisa verificar a branch, o estado local e a política do 
projeto antes dessas operações.
8.4 Pull request
Pull request é um recurso da plataforma para propor a integração de uma branch. Ele reúne a 
descrição da mudança, a comparação dos arquivos, comentários e decisões de revisão. O nome 
pode confundir iniciantes: pull request não é o comando git pull.
O fluxo demonstrado pelo instrutor será criar uma branch, registrar um commit, enviar a branch, abrir 
uma pull request, revisar a diferença, integrar a proposta e atualizar a cópia local. A interface 
pertence ao GitHub, enquanto commits, branches e merge continuam sendo conceitos do Git.
8.5 Colaboração em equipe
Em uma equipe, o histórico serve como comunicação técnica. Branches separam trabalhos em 
andamento, commits explicam mudanças e pull requests permitem revisão antes da integração. As 
regras variam entre projetos. Algumas equipes exigem aprovação e testes automáticos; outras 
adotam fluxos mais simples.
O minicurso apresenta o mecanismo básico, não uma política universal. O estudante deve sair 
entendendo as peças do processo e sabendo que cada projeto define convenções adicionais.

9 O projeto Git Multiverse
9.1 Objetivo conceitual
O Git Multiverse mostra a diferença entre trabalhar em branches independentes e integrar seus 
históricos. A temática Marvel e DC facilita a identificação das duas linhas de desenvolvimento, mas o 
conteúdo dos personagens é secundário. O objetivo é observar o comportamento do Git.
O projeto usa três arquivos Markdown. README.md representa a base comum. marvel.md nasce na 
branch universo-marvel. dc.md nasce na branch universo-dc. O uso de arquivos separados evita 
um conflito obrigatório e permite concentrar a atenção nos commits, nas branches e nos merges.
9.2 História esperada
Primeiro, main recebe o commit que cria README.md. Nesse ponto são criadas as duas branches. Os 
três nomes apontam para o mesmo commit inicial.
Em universo-marvel, o aluno cria e registra marvel.md. Depois muda para universo-dc, que ainda 
aponta para a base inicial, e registra dc.md. As duas branches agora possuem caminhos diferentes 
com o mesmo ancestral.
Por fim, o aluno volta para main. O primeiro merge integra Marvel e cria um commit de merge. O 
segundo integra DC e cria outro commit de merge. main passa a conter os três arquivos, enquanto 
os nomes das branches dos universos continuam apontando para seus commits exclusivos.
9.3 Leitura do grafo
O comando git log --oneline --graph --all --decorate deve mostrar cinco commits. Os hashes 
serão diferentes em cada computador, mas a estrutura deverá ser equivalente. O grafo mostra uma 
base comum, dois caminhos independentes e duas integrações sequenciais.
Ler esse grafo é mais importante do que decorar o desenho. O aluno deve conseguir apontar o 
commit inicial, os commits Marvel e DC e os dois commits que integraram os universos. Também 
deve explicar por que DC não nasceu de Marvel.
10 Erros comuns e formas de raciocinar
10.1 Pasta errada
Quando o Git informa que a pasta não é um repositório, o problema costuma ser o diretório atual. 
pwd mostra onde estamos. ls ajuda a reconhecer os arquivos. A correção é entrar na pasta correta 
com cd, sem executar sudo git ou criar outro repositório por impulso.
10.2 Identidade ausente
Se o commit falhar por falta de nome ou e-mail, configuramos a identidade local e repetimos o 
commit. Os arquivos preparados continuam na área de preparação. Não é necessário repetir a 
criação do arquivo ou o git add sem antes consultar git status.
10.3 Arquivo não preparado
Se o commit não inclui a mudança esperada, verificamos se o arquivo foi salvo e preparado. git 
status, git diff e git diff --cached mostram onde está o conteúdo.
10.4 Branch errada

11 Compatibilidade com Fedora e Linux Mint
Os comandos Git usados no minicurso funcionam no Bash do Fedora e do Linux Mint. Comandos 
como pwd, cd, mkdir, printf e cat também fazem parte do ambiente comum previsto para a aula.
Git e VS Code já estarão instalados. Se uma instalação excepcional for necessária antes do evento, 
Fedora usa dnf, enquanto Linux Mint usa ferramentas da família APT. Essa diferença pertence à 
preparação do laboratório e não deve consumir o tempo da aula. Os alunos não executarão 
comandos de instalação.
Diferenças entre versões do Git podem afetar git init -b main e git switch. Em uma versão 
antiga, as alternativas são git init seguido de git branch -M main, e git checkout no lugar de git 
switch. O instrutor deve verificar git --version nas máquinas antes da aula.
12 Síntese para o instrutor
O encadeamento conceitual do minicurso é simples. O controle de versão resolve o problema de 
compreender a evolução de um projeto. Git registra essa evolução localmente por meio de commits. 
A área de preparação permite escolher o conteúdo do próximo commit. Branches criam linhas de 
desenvolvimento, e merge integra essas linhas. GitHub hospeda repositórios e acrescenta recursos 
de colaboração, como pull requests.
Ao explicar qualquer comando, relacione-o a esse modelo. git status descreve o estado; git add 
prepara conteúdo; git commit registra uma versão; git switch muda a linha de trabalho; git merge 
integra históricos; git clone copia um repositório; git push envia commits; git pull obtém e 
integra atualizações. Quando o aluno entende o efeito de cada ação, deixa de depender da 
memorização de uma sequência mecânica.
